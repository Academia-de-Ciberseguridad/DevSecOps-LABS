La pieza de la que no hablamos

¿Quién ejecuta todo eso, y cuándo?

Un orquestador de CI/CD es el programa que:

  • Escucha un evento (un push, una hora, un botón).
  • Lee un fichero con la receta (el pipeline).
  • Ejecuta cada paso en el orden correcto, en una máquina limpia.
  • Guarda logs, informes y artefactos.
  • Decide si el resultado es verde, amarillo o rojo.
GitLab CI es un orquestador que viene dentro de GitLab.
Jenkins es un orquestador independiente: no le importa dónde esté tu código.

Otros orquestadores que verás

Jenkins GitLab CI GitHub Actions Azure DevOps TeamCity CircleCI Bamboo Argo / Tekton

Cambia la sintaxis. No cambian los conceptos: etapas, artefactos, credenciales, agentes, quality gates.

Qué es Jenkins

Historia mínima, arquitectura y el vocabulario que vas a usar toda la práctica.
Definición

Jenkins en una frase

Jenkins es un servidor de automatización de código abierto: un programa que ejecuta tareas (jobs) de forma automática cuando ocurre algo, y te enseña el resultado.

Historia (30 s)

  • 2004 — nace como Hudson en Sun Microsystems.
  • 2010 — Oracle compra Sun y se queda la marca Hudson.
  • 2011 — la comunidad hace fork y lo llama Jenkins.
  • 2016 — Jenkins 2.0: llega el Pipeline as Code (el Jenkinsfile).
  • Hoy — proyecto de la Continuous Delivery Foundation, +1.800 plugins.

Por qué te lo vas a encontrar sí o sí

  • Es el CI/CD con más despliegues on-premise del mundo.
  • Banca, industria, defensa, telco: entornos sin conexión a internet.
  • Agnóstico: GitHub, GitLab, Bitbucket, SVN, un directorio local…
  • Gratis y auto-hospedado: tú controlas dónde corren los datos.

Y por qué a veces duele

  • Hay que mantenerlo: actualizaciones, plugins, backups.
  • Los plugins son superpoder y deuda técnica a la vez.
  • La UI es… veterana.
  • Mal configurado es un objetivo de ataque de primer nivel.
Arquitectura

Controller, agentes, executors y workspace

   ┌───────────────────────────────────────────────┐
   │  JENKINS CONTROLLER  (el que ves en el navegador)│
   │  · guarda la configuración y el historial     │
   │  · decide QUÉ job se ejecuta y DÓNDE          │
   │  · NO debería ejecutar trabajo pesado         │
   └───────────────┬───────────────────────────────┘
                   │  reparte trabajo
       ┌───────────┼───────────┐
       ▼           ▼           ▼
   [ AGENTE 1 ] [ AGENTE 2 ] [ AGENTE n ]
   Linux/Windows/contenedor/Kubernetes
       │
       └─ cada agente tiene N EXECUTORS
          (= cuántos jobs a la vez puede correr)
          y cada build usa un WORKSPACE
          (= carpeta de trabajo con tu código)
En nuestro laboratorio hay un solo nodo: el built-in node (el propio contenedor de Jenkins). Suficiente para aprender; en producción nunca se ejecutan builds en el controller.

El alma (y el talón de Aquiles) de Jenkins

Plugins

Jenkins base hace muy poco. Casi todo lo que usarás es un plugin: hasta git y pipeline lo son.

Cuidado: superficie de ataque

  • Cada plugin es código de terceros con permisos totales sobre tu Jenkins.
  • Jenkins es históricamente uno de los productos con más CVEs por plugins.
  • Un Jenkins comprometido = todas tus credenciales de despliegue.

Buenas prácticas: instala solo lo necesario, revisa los avisos de seguridad (Manage Jenkins ▸ Security), y actualiza con ventana de mantenimiento.

Concepto crítico en DevSecOps

Credentials: los secretos NUNCA van en el Jenkinsfile

El Jenkinsfile vive en git. Todo lo que escribas dentro, lo verá todo el que tenga acceso al repo… y quedará en el historial para siempre.

Tipos de credencial que usaremos

TipoEjemplo de hoy
Username with passwordusuario root + PAT de GitLab
Secret texttoken de SonarQube, API key de DefectDojo
SSH private keyclonar por SSH, desplegar en un servidor
Secret filekubeconfig, certificados

Cómo se usan

// El secreto se inyecta SOLO en la etapa que lo necesita
withCredentials([string(
      credentialsId: 'sonar-token',
      variable: 'SONAR_TOKEN')]) {
  sh '... -Dsonar.token=$SONAR_TOKEN'
}

También existe environment { X = credentials('id') } para todo el pipeline, pero si el ID no existe el build muere antes de la primera etapa.

Jenkins enmascara el valor en la consola: verás **** en vez del token.
Comillas simples en sh '…': con sh "…${TOKEN}" Groovy incrusta el secreto y el enmascarado deja de funcionar.

El Jenkinsfile

Pipeline as Code: tu automatización, versionada como el resto del proyecto.
Pipeline declarativo

Anatomía de un Jenkinsfile

pipeline {
  agent any                    // DÓNDE se ejecuta

  options {                    // CÓMO se comporta el job
    timestamps()
    timeout(time: 30, unit: 'MINUTES')
  }
  parameters {                 // QUÉ te pregunta al lanzarlo
    booleanParam(name: 'RUN_DAST', defaultValue: false)
  }
  environment {                // variables para TODO el pipeline
    SONAR_HOST_URL = 'http://devsecops-sonarqube:9000'
  }
  stages {                     // EL TRABAJO, en bloques
    stage('Checkout') { steps { git url: '...' } }
    stage('Analizar') { steps { sh './analiza.sh' } }
  }
  post {                       // SIEMPRE al final, pase lo que pase
    always  { archiveArtifacts artifacts: '*.json' }
    failure { echo 'Algo ha fallado' }
  }
}

Declarativo vs Scripted

Declarativo (el que usamos): estructura fija, más legible, errores claros. Scripted: Groovy puro, todo poder y toda la responsabilidad.

Empieza siempre en declarativo; si necesitas lógica, mete un bloque script { … } dentro.

Se llama exactamente Jenkinsfile, sin extensión, en la raíz del repositorio. Igual que .gitlab-ci.yml lo era para GitLab.

Semáforo

Verde, amarillo, rojo: el resultado es la decisión de seguridad

🟢 SUCCESS

Todo pasó. Nada que reportar.

En seguridad: ninguna herramienta encontró nada por encima del umbral.

🟡 UNSTABLE

Terminó, pero con hallazgos. Step: unstable('…')

En seguridad: "hay vulnerabilidades, míralas" — avisa pero no bloquea.

🔴 FAILURE

Se abortó. Step: error('…')

En seguridad: el quality gate. Nada avanza hasta que se arregle.

Traducción desde GitLab CI: lo que allí hacías con allow_failure: true (avisar) aquí es unstable(); y allow_failure: false (bloquear) aquí es error(). Mismo concepto, otra sintaxis.

También existe ABORTED (alguien lo canceló o saltó el timeout) y NOT_BUILT (una etapa que se saltó por una condición when).

¿Cuándo se lanza un pipeline?

Disparadores

DisparadorCómo funciona
Manual hoyBotón Build Now. Perfecto para aprender.
WebhookGitLab/GitHub avisa a Jenkins en cuanto hay push. Lo estándar en producción.
SCM PollingJenkins pregunta cada X minutos "¿hay algo nuevo?". Simple pero derrochador.
CronH 2 * * * — escaneos nocturnos completos.
UpstreamSe lanza cuando termina otro job.
Por qué hoy lo lanzamos a mano: con 15 personas y un solo servidor, los webhooks dispararían pipelines a la vez y se saturaría. En tu empresa, el webhook es lo normal.

Patrón real en seguridad

  • Por push: lo rápido (secretos, SAST, SCA) — segundos o pocos minutos.
  • Cada noche: lo lento (DAST completo, escaneo de todas las imágenes).
  • Por release: el quality gate duro que bloquea el despliegue.

Jenkins + Docker

Cómo un Jenkins que no tiene instalado nada consigue ejecutar Trivy, ZAP o SonarQube.
El truco central del laboratorio

Jenkins no tiene las herramientas: las lanza en contenedores

   ┌── contenedor devsecops-jenkins ─────────────┐
   │  Jenkins + cliente `docker`                │
   │                                            │
   │   sh 'docker run ... aquasec/trivy ...'    │
   │            │                               │
   └────────────┼───────────────────────────────┘
                │  a través de /var/run/docker.sock
                ▼
   ┌── DEMONIO DOCKER DEL HOST ──────────────────┐
   │                                            │
   │   crea un contenedor HERMANO, no hijo:     │
   │   [gitleaks] [trivy] [sonar-scanner] [zap] │
   └────────────────────────────────────────────┘

Se llama DooD — Docker out of Docker. Le montamos a Jenkins el socket del demonio Docker del host, así que sus docker run crean contenedores al lado del suyo, no dentro.

La ventaja

Jenkins se mantiene limpio. ¿Necesitas otra versión de Trivy? Cambias una etiqueta de imagen. Nada que instalar, nada que desinstalar.

La advertencia de seguridad

Quien pueda escribir un pipeline en este Jenkins puede hacer lo que quiera en el host: el socket de Docker equivale a root.

En producción: agentes efímeros, Kubernetes, o buildkit/kaniko sin socket. En el laboratorio lo aceptamos a propósito, y hay que saberlo.

Si algún día "el escáner no encuentra nada"…

El fallo clásico: las rutas del workspace

Cuando el pipeline ejecuta:

docker run -v "$WORKSPACE":/src aquasec/trivy fs /src

…esa ruta NO la interpreta Jenkins. La interpreta el demonio Docker del host, que no sabe nada del sistema de ficheros interno del contenedor de Jenkins.

Si la ruta no existe también en el host, Docker no da error: crea un directorio vacío y lo monta. Resultado: el escáner analiza la nada y dice "0 vulnerabilidades". Un falso verde: lo peor que puede pasar en seguridad.

Cómo lo resolvemos

Montamos JENKINS_HOME con la misma ruta dentro y fuera:

volumes:
  - /var/jenkins_home:/var/jenkins_home

Así $WORKSPACE apunta al mismo sitio en los dos mundos.

Comprobación rápida en clase: añade un ls -la /src dentro del contenedor. Si sale vacío, es esto.

De "informar" a "impedir"

El quality gate: cuando la seguridad tiene dientes

// Gitleaks devuelve 1 cuando ENCUENTRA secretos:
// no es un error de ejecución, es un HALLAZGO.
int rc = sh(returnStatus: true, script: 'docker run ... gitleaks detect ...')

if (rc == 0) {
    echo 'Sin secretos'                        // 🟢
} else if (params.BLOQUEAR_SI_HAY_SECRETOS) {
    error('QUALITY GATE: secretos detectados')  // 🔴 aborta
} else {
    unstable('Secretos detectados (aviso)')      // 🟡 continúa
}

Fíjate en returnStatus: true: sin eso, sh aborta el pipeline en cuanto el comando devuelve algo distinto de 0 y nunca llegarías a decidir.

Cómo se implanta en la vida real

  1. Fase 1 — Observar: todo en amarillo. Nadie se bloquea; se mide cuánta deuda hay.
  2. Fase 2 — Congelar: bloquea solo lo nuevo (no empeorar).
  3. Fase 3 — Bloquear: critical y secretos rompen el build, sin excepciones.

Empezar por la fase 3 el primer día es la forma más rápida de que el equipo desactive la seguridad.

Nivel 1 · 10 minutos

Tu primer pipeline: "Hola, Jenkins"

1New Item (menú izquierdo) → nombre pipeline-TUNOMBRE → tipo Pipeline → OK.

2Baja hasta la sección Pipeline, deja Definition: Pipeline script y pega:

pipeline {
  agent any
  stages {
    stage('Saludo') {
      steps {
        echo "Hola, soy el build #${env.BUILD_NUMBER}"
        sh 'date; whoami; pwd'
      }
    }
    stage('¿Tengo Docker?') {
      steps { sh 'docker version --format "Servidor: {{.Server.Version}}"' }
    }
  }
}

3Save → Build Now → clic en el build #1 → Console Output.

Qué acabas de ver

  • El Stage View: una columna por etapa, con su tiempo.
  • El Console Output: el log completo. Aquí se depura todo.
  • whoami → root; pwd → tu workspace.
  • Jenkins sí puede hablar con Docker: eso es lo que hará el trabajo pesado.
Rompe algo a propósito: cambia sh 'date' por sh 'fecha' y vuelve a lanzar. Mira cómo se pone en rojo y cómo el log te dice exactamente qué línea falló.
Nivel 2 · 15 minutos

Código real + un escáner de seguridad de verdad

1Credencial de GitLab — Manage Jenkins ▸ Credentials ▸ System ▸ Global ▸ Add Credentials: Username with password, usuario root, contraseña tu PAT, ID gitlab-cred-TUNOMBRE. 2Job → Configure → sustituye el script:

pipeline {
  agent any
  stages {
    stage('Checkout') {
      steps { git url: 'http://devsecops-gitlab:8929/root/devsecops-sample.git',
                  branch: 'main', credentialsId: 'gitlab-cred-TUNOMBRE' }
    }
    stage('Secretos') {
      steps {
        sh '''docker run --rm -v "$WORKSPACE":/src -w /src \
              ghcr.io/gitleaks/gitleaks:v8.18.4 detect --source /src \
              --report-format json --report-path /src/gitleaks-report.json \
              --redact --verbose || true'''
      }
    }
  }
  post { always { archiveArtifacts '*.json' } }
}

Fíjate en 3 cosas

  • La URL usa devsecops-gitlab, no localhost: el job vive en la red Docker.
  • El token no está en el script: está en Credentials.
  • -v "$WORKSPACE":/src le da al contenedor de Gitleaks tu código.
Resultado: 1 hallazgo — regla aws-access-token en app.py:23.
¿Y las otras dos claves de app.py? Gitleaks va por patrones conocidos; SuperSecret123! no parece nada. Falso negativo — pero SonarQube sí lo caza. Ninguna herramienta sola basta.

Reto final · el que de verdad importa

Convierte el aviso en un bloqueo

1Lanza el pipeline con Build with Parameters y marca BLOQUEAR_SI_HAY_SECRETOS.

2Observa: el build pasa de 🟡 amarillo a 🔴 rojo y las etapas siguientes ni se ejecutan.

3Ahora arréglalo: en una rama, saca el secreto de app.py, push, y relanza con GIT_BRANCH=fix-secretos.

# antes
AWS_SECRET = "AKIAIOSFODNN7FAKEFAKE"
# después
AWS_SECRET = os.environ.get("AWS_SECRET")

4Sigue en ROJO. Gitleaks no analiza solo el código: analiza todo el historial de git, y el commit viejo sigue ahí.

La lección de la clase: un secreto commiteado está quemado. Borrarlo del fichero no lo borra de la historia, ni de los forks, ni de los backups. Lo único que sirve es rotar la credencial.

Si te sobra tiempo

  • Activa RUN_DAST y mira la pestaña Informe OWASP ZAP del build.
  • Añade --exit-code 1 a Trivy para bloquear por CVEs críticos.
  • Programa el job cada noche: Build Triggers ▸ Build periodically ▸ H 2 * * *.

Jenkins también es un activo que hay que proteger

Asegurar el propio servidor de CI

Por qué es un objetivo goloso

  • Guarda todas las credenciales de despliegue: cloud, registries, producción.
  • Puede ejecutar código arbitrario por diseño: es su función.
  • Suele tener acceso de red a producción.
  • Con el socket de Docker montado, un pipeline malicioso = root en el host.

Comprometer el CI es comprometer toda la cadena de suministro del software.

Controles mínimos

  • Nunca expuesto a internet sin VPN/SSO. Y con HTTPS.
  • RBAC real (Matrix Authorization): no todos administradores.
  • Builds en agentes efímeros, jamás en el controller.
  • Plugins mínimos y actualizados; revisar los avisos de seguridad.
  • Secretos en Credentials (o Vault), nunca en el Jenkinsfile.
  • Backup de JENKINS_HOME y auditoría de quién cambia jobs.
Nuestro laboratorio incumple varias de estas a propósito (Jenkins como root, socket montado, todos administradores). Está bien saberlo: un lab no es producción.
Resumen

Las 8 ideas que deberías recordar mañana

1Jenkins es un orquestador: no analiza nada, llama a quien analiza.

2Pipeline as Code: la receta vive en el repo, en un Jenkinsfile.

3Controller + agentes + executors: quién manda, quién ejecuta y cuántos a la vez.

4Credentials: los secretos, fuera del código y enmascarados en el log.

5Contenedores como herramientas: Jenkins limpio, versiones controladas.

6Verde / amarillo / rojo es una decisión de seguridad, no un color.

7Quality gate progresivo: primero medir, después congelar, al final bloquear.

8El CI es un activo crítico: protégelo como protegerías producción.

Y la más importante: lo que aprendiste con GitLab CI te sirvió intacto aquí. Las herramientas cambian cada 3 años; los conceptos, no.
